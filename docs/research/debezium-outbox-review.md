# debezium/debezium-examples outbox review

Studied: https://github.com/debezium/debezium-examples/tree/dbac92d24c5f84f95d8a2799210433ef4739b31d/outbox @ `dbac92d24c5f84f95d8a2799210433ef4739b31d`, 2026-11-20; maintenance: active (pinned HEAD commit dated 2026-11-19). Feeds: P0.3 → ADR-005 outbox, transport identity and source-cut handoff.

| Component studied | Lesson | Decision for METERPROOF | Trade-off | Test that proves it |
|---|---|---|---|---|
| `outbox/README.md`, `register-postgres.json`, `docker-compose.yaml` | The sender writes outbox events in its local database; the Debezium PostgreSQL connector captures the outbox table and the Outbox Event Router routes by aggregate type. The sample connector selects `inventory.outboxevent`, routes to `<aggregate-type>.events`, and places event type in a header. | Use an app-owned transactional outbox for METERPROOF `source_event_id`; route app, provider and invoice sources to versioned topics. Keep the source event identity in the event envelope/header and choose a separate partition key appropriate to each source. | Requires outbox schema/retention and connector configuration; duplicate delivery remains possible and must be idempotent. | T01 verifies a redelivery is retained in raw audit but applies one canonical side effect; P2.2/P4.1 exercise the real connector. |
| `order-service` `OrderService.java` and `OrderCreatedEvent.java` / `InvoiceCreatedEvent.java` | Domain operations are `@Transactional` and emit typed events with aggregate ID/type, event type, timestamp and payload, aligning intent and outbox creation to a database transaction. | Persist source receipt/outbox event in the same PostgreSQL transaction. `source_event_id` remains the outbox row identity; it is not derived from a Kafka offset. | Transaction coupling requires a stable outbox contract and explicit schema evolution. | T01 plus source-cut checks compare committed source event IDs to Debezium/Kafka observations. |
| `shipment-service` `KafkaEventConsumer.java`, `OrderEventHandler.java`, `MessageLog.java` | The consumer reads the outbox event ID from a Kafka header, checks a consumed-message table, applies the side effect and writes its idempotency log transactionally, then manually acknowledges after handler completion. | Deduplicate canonical side effects on `(tenant_id, source_event_id)`; retain every raw `transport_delivery_id=(topic, partition, offset)` separately for audit. | The consumer log/side effect transaction and source event store must share a transaction boundary or use an idempotent sink contract. | T01 redelivery test and T03 crash after sink commit/before ACK, followed by restart and sink reconciliation. |
| `outbox/test.yaml` | The example waits for connector RUNNING, waits a fixed 15 seconds for a snapshot, then verifies events; it does not stop/restart the connector or prove a crash/recovery boundary. | Treat the sample as a wiring pattern only. METERPROOF's snapshot-to-stream handoff must prove source-event coverage, LSN/offset correspondence, completed checkpoint and sink receipt under its own tests. | More operational evidence is needed than the example's smoke flow; WAL slot monitoring and restart drills are required before any reliability claim. | T01, T03 and T10 in P2.2/P4.1; until those run, the cut is NOT_COMPARABLE if coverage evidence is missing. |

Not adopted and why: no example code or schema copied, and no dependency added. The order/shipment sample demonstrates an outbox/router and consumer event-ID dedupe; it does not establish METERPROOF's provider/invoice completeness, its WAL lifecycle, or an end-to-end delivery guarantee. The test's fixed snapshot delay is not used as a cut proof.
